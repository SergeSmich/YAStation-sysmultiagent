# Шина команд через GitHub Issues

Дополнительный канал управления станцией: команда приезжает как issue, исполняется
локально наблюдателем (`scripts/arena_watcher.py`), результат возвращается комментарием
в тот же issue. Git-мост (`AGENTS.md`, `collab/`) при этом не меняется — это второй,
независимый путь. Шина **выключена по умолчанию**: пока watcher не запущен, поведение
станции ровно такое же, как сейчас.

## Что это не

Чего шина не делает принципиально, а не «пока не реализовали»:

- не исполняет произвольные строки — только фиксированный набор действий с
  проверенными аргументами, без склейки shell-команд (`shell=False`, argv списком);
- не пишет в репозиторий: ни `git push`, ни коммитов, ни правки файлов;
- не разворачивает и не перезапускает сервисы (`build` — только сборка, без деплоя);
- не «прокидывает» токены: дочерние процессы получают урезанное окружение,
  GitHub-доступ есть только у `gh`;
- не является каналом переписки — обсуждение задач остаётся в `collab/`.

Практическое следствие: компрометация issue (или аккаунта автора) даёт максимум
чтение состояния станции — `git status`, хвост лога, результаты тестов, healthz.

## Роли

| Роль | Кто это | Что делает |
| --- | --- | --- |
| Arena | агент в чате | открывает issue `oc:run`, читает комментарии-результаты |
| наблюдатель (watcher) | процесс на станции | забирает issue, исполняет, комментирует, ставит метку |
| оператор | владелец машины | держит конфиг и allowlist логинов, запускает/останавливает watcher, арбитр при инциденте |

Наблюдатель — единственная сторона, которая что-то исполняет. Он никого не «слушает»
напрямую: единственный вход — issue с меткой `oc:run`, единственный выход — комментарий
и метка.

## Поток

```
Arena                    GitHub                     watcher (станция)
  |                        |                             |
  |-- issue + oc:run ----->|                             |
  |                        |<---- список oc:run ---------|
  |                        |                             | проверка автора
  |                        |<---- +oc:running, -oc:run ---|
  |                        |----- перечитать issue ------>| сверка sha256 тела
  |                        |                             | исполнение
  |                        |<---- комментарий-результат ---|
  |                        |<---- -oc:running, +oc:done ---|
  |<--- читает результат --|                             |
```

Порядок в `claim_and_run` важен: метка `oc:running` ставится **до** исполнения, иначе
второй проход цикла (или второй watcher) возьмёт ту же команду.

## Формат issue

Тело: один fenced-блок ```` ```json ```` и, при желании, любой текст вокруг. Больше
одного блока — отказ (нельзя «спрятать» вторую команду в пояснении).

````markdown
Проверить, что после правок не сломались тесты бриджа.

```json
{
  "id": "CMD-0012",
  "action": "run_tests",
  "args": {"packages": ["./internal/bridge"]},
  "timeout_s": 180,
  "note": "после L-0002"
}
```
````

Поля:

| Поле | Обязательно | Правило |
| --- | --- | --- |
| `id` | да | `CMD-NNNN` (`^CMD-[0-9]{4,6}$`), попадает в комментарий и лог |
| `action` | да | одно из перечня ниже |
| `args` | нет | объект; лишние ключи — отказ, а не игнор |
| `timeout_s` | нет | 1..`max_timeout_s` (600 по умолчанию), больше — обрезается |
| `note` | нет | строка ≤ 200 символов, попадает в комментарий как примечание |

Неизвестные поля верхнего уровня (`shell`, `cwd`, `env`, …) — отказ. Тело больше
`max_body_bytes` (16 КиБ) — отказ без разбора.

## Метки

| Метка | Кто ставит | Смысл |
| --- | --- | --- |
| `oc:run` | Arena | «команда готова к исполнению», триггер |
| `oc:running` | watcher | «забрал, исполняю»; держится до комментария |
| `oc:done` | watcher | исполнено, exit 0 |
| `oc:failed` | watcher | отказ, ошибка или зависание |
| `oc:paused` | оператор | «не трогать этот issue» (проверяется первым) |

`oc:paused` удобен, чтобы придержать заведомо тяжёлую команду, не снимая `oc:run`.
Локальный стоп — файл `.arena/paused`: пока он есть, цикл не делает ничего, включая
чтение GitHub.

Метки создаются один раз: `python scripts/arena_watcher.py --init-labels`.

## Идемпотентность и зависания

- **Повторный проход.** Issue с `oc:running` не исполняется: это либо работа в
  процессе, либо брошенная команда. Отличить их по метке нельзя, поэтому вторая
  попытка не делается.
- **Сверка тела.** После `oc:running` watcher перечитывает issue и сравнивает
  `sha256` тела с тем, что был прочитан до claim. Разошлось → `oc:failed`,
  комментарий «body changed», команда не исполняется. Так правка тела «на лету»
  не превращается в исполнение непроверенного текста.
- **Зависание.** `oc:running` старше `stale_running_min` (15 мин по умолчанию) →
  комментарий «не выполнено», снятие `oc:running`, `oc:failed`. **Автоматического
  перезапуска нет**: оператор смотрит, что было, и решает, ставить ли `oc:run` снова.
  Иначе зависший `go test` перезапускался бы бесконечно.
- **Крэш watcher'а.** Метка `oc:running` остаётся и «созревает» через 15 минут —
  это и есть путь восстановления. Полуисполненных состояний шина не создаёт:
  действия либо читают, либо пишут только в `.arena/`.

## Доверие

Команда исполняется, только если выполнены оба условия:

1. `author_association` ∈ {`OWNER`, `MEMBER`, `COLLABORATOR`};
2. `user.login` входит в `allowed_logins` конфига (сравнение без учёта регистра).

Пустой `allowed_logins` — ошибка конфигурации, а не «доверять всем»: иначе на публичном
репозитории любой коллаборатор получал бы доступ к станции.

Недоверенный автор: метка `oc:run` снимается, команда не исполняется, в issue **не
пишется ничего** (ответ подтвердил бы существование шины и её формат), в локальный лог
попадает строка `untrusted` с логином. Если нужен явный отказ — это делает оператор
руками.

Все проверки — до исполнения: доверие → разбор → аргументы → claim. Поэтому
недоверенная команда не может «дойти» до `run_tests` даже с валидным JSON.

## Публичность и секреты

Шина рассчитана на приватный репозиторий, но исходит из худшего: тело issue и
комментарии публичны.

- В теле issue — никаких токенов, паролей, адресов и серийников. Команда и так их не
  принимает, но тело остаётся в истории issue навсегда.
- Вывод перед публикацией проходит `redact` (ключи вида `token=`, `password:`,
  `Authorization:`, GitHub-токены, JWT, приватные ключи) и `clip`
  (`max_result_bytes` 8000, `max_result_lines` 60) с пометкой «(обрезано)».
- `deploy_check` публикует только `label` из конфига и код/время ответа: URL
  (внутренний адрес станции) в issue не попадает.
- `read_log` работает только внутри `allow.log_dirs` (`logs/`), хвост ≤ 200 строк;
  `..`, абсолютные пути и управляющие символы отбрасываются.

Редакция — ремень, а не гарантия: перед публикацией лога убедись, что в нём нет того,
чего не должно быть в истории issue.

## Команды v1

| `action` | `args` | Что делает | Границы |
| --- | --- | --- | --- |
| `git_status` | — | `git status --porcelain=v1 --branch` | только чтение |
| `git_log` | `n` | последние коммиты, `--pretty=%h %ad %s` | `n` ≤ 30 |
| `run_tests` | `packages` | `go test <пакеты>` | пакеты только из `allow.test_package_re`, ≤ 8 |
| `build` | — | `go build -o .arena/build/ ./...` | артефакты вне дерева, без деплоя |
| `read_log` | `path`, `lines` | хвост файла из `logs/` | ≤ 200 строк, без выхода за каталог |
| `grep` | `pattern`, `glob`, `max` | поиск по репозиторию | `glob` из `allow.grep_globs`, `max` ≤ 200 |
| `deploy_check` | `url` | GET healthz | только `health[]` из конфига, read-only |

`run_tests` без `packages` берёт `allow.default_test_packages`. `grep` без `glob`
идёт по всем `allow.grep_globs`, пропускает `.git`, `.arena`, `node_modules`, `dist`,
`build`, `__pycache__`, файлы > 512 КиБ и не больше 2000 файлов.

## Как читать результат

Комментарий начинается с заголовка `### oc:result CMD-NNNN — action` и содержит
статус (`ок`/`ошибка`), `exit` код, длительность и её лимит, первые 16 символов
`sha256` тела (по ним видно, что исполнено ровно то, что читали), объём вывода и сам
вывод в блоке ```` ```text ````. Отказ (`deploy`, кривой JSON, лишний ключ) выглядит
так же, но с пометкой «отклонено» и причиной — исполнения не было.

Метка после комментария: `oc:done` при exit 0, `oc:failed` иначе.

## Ограничения

- Команда — один issue; скриптов и пайплайнов нет намеренно.
- Вывод обрезан: длинный `go test` придёт хвостом, полный лог — через `read_log`
  по файлу, который пишет CI/сервис, а не через бесконечный комментарий.
- `build` не публикует артефакты и ничего не устанавливает.
- Сеть: `deploy_check` ходит только по адресам из конфига; произвольный URL
  недоступен.
- Windows: watcher сам ставит UTF-8 и берёт `gh.exe`/`git.exe` по `PATH`; путь к ним
  можно задать в конфиге (`gh`, `git`, `go`).
- Один watcher на машину: второй экземпляр не стартует (lock `.arena/watcher.lock`).
- За проход читается не больше 50 открытых issue на каждую метку (`per_page=50`, без
  постраничного обхода): очередь длиннее разбирается за несколько проходов.

## Как включить

1. Скопировать пример **вне** отслеживаемого дерева и заполнить:

   ```bash
   mkdir -p .arena
   cp scripts/arena_watcher.example.json .arena/watcher.json
   ```

   Заменить `repo`, `workdir`, `allowed_logins`, `health[].url`. `workdir` — корень
   этого репозитория на станции. Живой конфиг содержит адреса машины, поэтому в git
   он не попадает (`.arena/` уже в `.gitignore`).

2. Проверить конфиг, ничего не запуская: `python scripts/arena_watcher.py --check-config`.

3. Создать метки (один раз, нужен `gh auth login`): `--init-labels`.

4. Сухой прогон: `--once --dry-run --verbose` — watcher перечислит, что бы он сделал,
   не меняя ни меток, ни issue, ни исполняя команды.

5. Боевой одиночный проход: `--once`. Убедиться, что комментарий и метки появились.

6. Поставить в автозапуск. Windows (Планировщик) или Linux (systemd, пример юнита):

   ```ini
   [Service]
   ExecStart=/usr/bin/python3 scripts/arena_watcher.py --config .arena/watcher.json
   WorkingDirectory=.
   Restart=on-failure
   ```

   Остановка: снять юнит/задачу либо создать `.arena/paused` (мягкий стоп без
   выхода процесса), либо `Ctrl+C`.

Лог — `.arena/watcher.log`, JSONL по событиям: `start`, `untrusted`, `rejected`,
`body_changed`, `executed`, `stale_running`, `poll_failed`, `stop`.

## Как откатить

Откат не требует правок кода — шина вся в одном процессе:

1. Остановить watcher (юнит/задача/`Ctrl+C`).
2. Удалить `.arena/watcher.json` (и `.arena/watcher.lock`, если процесс убивали жёстко).
3. При желании снять метки `oc:*` с открытых issue и удалить их из репозитория.

После этого станция ведёт себя ровно как до включения: issue с `oc:run` просто никто
не читает. Комментарии-результаты остаются историей в issue — при необходимости
закрыть issue руками. Git-мост, `collab/bridge.json` и Go-код шина не затрагивает,
так что откат шины не влияет на обмен задачами через `L-*`/`A-*`.
